# 分区读写只做镜像级，且危险分区标记但不禁用

「读写分区」在中文搞机语境里同时指两件完全不同的事——`dd` 整块读写（镜像级）和 `mount -o rw,remount` 后改文件（挂载级）。本仓库的分区读写功能只做前者，并且分区列表全量列出、只给危险分区打 ⚠ 标记而不禁用它们。

**为什么只做镜像级**：挂载级在 Android 12+ 要同时处理 dm-verity、super 逻辑分区和 overlay 三层，是另一个量级的活儿；而本仓库的主线场景（备份 boot、刷 magisk patched boot、救砖还原）用镜像级就够了。

**为什么不用白名单而是「标记但不禁用」**：白名单会在 LK、DSU 这类排障场景下束手无策——需要的时候恰恰不能选。变砖往往不是因为工具给了选项，而是给了却不说明后果，所以选择把风险显式写出来（⚠危险 / ⚠逻辑分区），把判断留给人。

## Amendment 1（2026-09-12）：对 `userdata` 改用禁止名单

真机验证后收窄：分区列表不再是「全量列出」，`userdata` 被移入**禁止分区**——不展示、脚本也拒绝读写。

原因有三，任一条都足够：整块写入必然丢光用户数据；读出来也没意义，它在本机型上是加密/映射设备，`dd` 得到的是乱码而非可用镜像；它还是最大的分区，是「全选」误伤的头号目标。「读也没意义」这一点是原决策时没有料到的，它让「标记但不禁用」的收益归零、只剩风险。

其余危险分区（`metadata`、`misc`、`persist` 等）仍维持「标记但不禁用」，本条不改动那部分决定。

## Consequences

- 危险分区可选意味着误操作路径存在，因此写入侧必须有独立的硬校验（稀疏镜像、大小、镜像头魔数），不能只靠 UI 标记。
- 组件库的多选弹窗固定带「全选」按钮且无法禁用单个 option（`DialogItemChooser` 的 `multiple` 是硬编码 `true`），所以「全选把 userdata 也选进来」只能在脚本侧拦：总大小预检 + 备份目录所在分区自举检测。
- 「镜像级读写」与「挂载级读写」已成为 `CONTEXT.md` 里的正式术语，文档和注释中不得裸用「读写分区」。
